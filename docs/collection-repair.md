# 采集时间窗口修复

## 原因

旧逻辑把上次成功查询的时间作为本次结果的发布时间下限。搜索不是完整索引，所以晚出现的、之前未收录的报道被误标为 baseline。2026-11-11 16:00 的游戏搜索因此只把一个时间较新的 IGN 收藏页送去评分。

## 新规则

- 窗口下限为 `max(now - 14天, min(now - (gap_days + 1)天, last_success))`。第一次没有 last_success 时采用专题间隔窗口。
- 首次查询也接纳窗口内有明确日期的新 URL。维持日期检查和未来 5 分钟容差。
- canonical URL 已排队/已评分则不重复；不同 URL 的同事件仍交给编辑处理。
- IGN `/playlist/` 目录明确排除。旧收藏页也不再出现在滚动列表中，但原评分留在数据库，不修改已发布日报。
- 不改变搜索次数、模型预算、Jev 提示或分数门槛；测试复现“9 条早于上次搜索的报道 + 1 个收藏页”，9 条均进入评分，收藏页被排除。

## 已存候选恢复

`src/site/recover-candidates.ts` 提供仅运维可调用的 `recoverMissedCandidates`，无公网入口。默认预览，不写库；显式 `apply:true` 才恢复。

- 只处理当前专题窗口内、从未判断过的 baseline，每次最多检查 500 条。
- 排除已判断、失败、已有 Jev 调用记录、无日期、过期、非新闻页面；同 URL 只恢复一个频道。
- 恢复前在已有 `site_judgment_history` 表保存来源状态及授权标识，随后将候选置为 pending。重复执行不重复排队。
- 恢复函数本身不搜索、不调用模型；恢复后普通 Cron 可按现有预算评分，因此生产应用前需要授权。
- 不伪造历史搜索成员关系，不重写旧滚动批次或已发布日报。恢复后的报道供普通新闻列表与未来日报选取。
