# 推送事件（暂未接入发送）

`src/site/push.ts` 将推送意图与搜索、Jev、发送渠道分离。没有额外模型调用，也没有 HTTP 发送、公网消费接口或消费端凭证。

## 触发规则

- 仅来自成功的小时滚动搜索（`site_search_items`），不含晨间搜索、手动日报和旧基线。
- 有效 v2 Jev 判断 `worthReading >= 0.8`，包含恰好 0.8；不限页面前三条。
- 评分延迟到后续 Cron 才完成也能捕获。
- 按个人用户 `owner` + canonical article ID 永久去重；跨频道、跨批次不重复。不做语义去重。
- 事件保存标题、HTTPS 原文地址、发布日期、原始概率、搜索批次和生成时间快照，不携带画像、反馈或提示词。

## 启用

当前默认关闭，生产尚未启用。部署前应用 `migrations/0014_push_events.sql`，然后设置：

```ini
PUSH_EVENTS_ENABLED=true
PUSH_EVENTS_SINCE=2026-11-11T08:00:00Z
```

`PUSH_EVENTS_SINCE` 是运维指定的启用时刻（示例而非自动默认值），不补录此前发起的搜索。每个正常 Cron 在评分之后独立执行 `capturePushEvents`；事件落库失败不把已成功的评分改成失败，不阻断日报。每次最多检查 100 条候选。

`site_push_events` 是不可变事件表，**不是已发送记录，也不代表已获准实际发送**。即便开启事件收集，也没有实际通知。未开放公开查询接口，未来消费协议和认证另行设计。

## 未来消费端契约

`PushTransport.send(event, { idempotencyKey, signal })` 仅定义适配器边界，当前没有实现或调度器。

接入前必须实现独立 D1 delivery 表/调度器：

1. 明确用户、目的端、每用户每日上限、有效期及安静时段（按用户本地时间）；历史积压不得直接全部发送。
2. 在网络调用前，事务性预留 delivery 和用户额度，并以 event + recipient 做唯一键。
3. 向消费端传稳定幂等键。收到 `accepted` 仅表示消费端接收，不代表用户已看到。
4. `rejected`、`unknown`、超时、异常及发送中进程中断均保留审计，不自动重发；未知结果需人工核对。
5. 目的端固定在可信配置中，不能使用新闻链接或模型输出作为 webhook 地址；保留 SSRF、超时、大小和认证限制。
6. 消费端把标题当纯文本显示，不执行其中的 HTML 或指令。重试策略、补发和新增渠道都需要另行确定。

不预设 Web Push、Webhook、App 或其他供应商，不改变已有通知模块的限额和预留机制。
